# Consultant response: Hearthline H1a data model and scope seam

Date: 2026-11-22. Reviewer: the independent consultant, read-only access to the repository. Verbatim review below, then what was applied.

**H1a verdict: keep the ownership model, but fix migration 5 before rollout.** It can commit an acquisition run whose owner differs from its search. Both SQLite checks pass, and deleting the search can then delete another owner’s run.

1. **Keep the XOR. Move rows in place when linking.** Set all three ownership columns in the same `UPDATE` and move the account’s records in one transaction across tables. Preserve IDs and references, including scenario references to forecasts. Define how to handle collisions with existing native profiles, eligibility records, and forecast hashes before linking ships. The current acquisition triggers block either update order for a search with runs. One workable linking procedure is to stage the runs inside the transaction, remove them, move the search, and reinsert the runs with their original IDs under the new scope. Drain in-flight scans during transfer and clear active alert destinations and schedule flags while P5 is pending. Update the migration comment to reflect that linking can preserve XOR. [Migration 5](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:153) · [Acquisition triggers](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:392)

2. **Keep both profile `UNIQUE` constraints.** XOR and the paired-scope check guarantee that one unique key is fully populated on every row. SQLite’s treatment of `NULL` lets the unused key coexist across rows. Separately, declare the surrogate `id` explicitly `NOT NULL`. I verified that the pre-H1a profile insert can create a v5 row with `id=NULL` because it omits the new column. Any rollback build allowed to write to v5 must supply the ID. Test legacy registration and first profile writes with that build. [Profile schema](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:164) · [Profile upsert](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/routes/product.py:59)

3. **Keep the 409 gate and the legacy job filters.** An enabled flag should mean the work can run. Require P5 worker authorization for scheduling and a verified destination for email. Add a scope guard at the actual email-send point. I verified that a native manual scan invokes the mocked sender if a persisted row has both an enabled flag and a recipient. Also make the documented 409 consistent: enabling native alerts without an email currently returns 422 from model validation before the scope guard runs. Preserve the legacy validation behavior and test both native request forms. [Alert guard](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/routes/product.py:100) · [Email send](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/routes/product.py:377) · [Request validation](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/routes/product_models.py:130)

4. **The empty-database restore is a good smoke test. Require a release rehearsal before H1b.**
   - On a representative v4 copy, take a verified pre-upgrade backup using the v4 runtime or a backup path that skips migrations. The candidate backup command calls `init_database()` before copying. Rehearse v4→v5 and restore with the app and jobs stopped. Compare counts and deterministic content digests for every retained table, including legacy owners and child rows. Assert the expected omission of licensed forecasts and acquisition runs, plus the expected behavior of surviving scenario references. Require foreign-key and owner-consistency checks before the restore tool replaces the target. Rehearse disabling the native path while keeping post-upgrade writes. [Backup and restore implementation](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/jobs/database_maintenance.py:20) · [Current restore drill](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/tests/test_platform_scope.py:262)
   - Test the real platform adapter and ingress with the feature flag on and off. A verified platform principal should win when both credentials are present. Invalid presented platform credentials should fail closed, and legacy sessions should still work on the legacy path. Verify active workspace membership and canonical subject and workspace IDs before building `Scope`. Repeat the read, write, and guessed-ID tests with real credentials for two subjects, two workspaces, and a legacy account. [Principal dependency](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/auth.py:161) · [Scope tests](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/tests/test_platform_scope.py:150)

5. **Fix the upgrade checks now and close the ownership-transfer race before linking.**
   - **Upgrade integrity.** Validate every copied run against its parent before recording v5. Use a null-safe comparison of all three owner fields, or copy with the owner trigger already active. A mismatch should abort the entire rebuild for explicit remediation. Add a v4 regression fixture where both users exist and the run references the other user’s search. Also cover a SQL failure during the copy itself. `executescript()` currently sits outside the runner’s explicit rollback handler, so that failure relies on the outer connection context for rollback. [Run copy and triggers](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:385) · [Migration runner](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:445)
   - **Concurrent startup.** Recheck the migration version after taking the write lock, or use a single designated migrator. Two initializers can both decide v5 is pending. I reproduced a stale initializer failing after the first committed, with the committed data intact. Also tighten the shape checks to reject embedded NULs, which the current SQLite checks accept. [Version selection](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:477) · [Shape checks](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/database.py:173)
   - **Scope isolation during transfer.** The ordinary scoped queries looked sound for fixed ownership. Saved-search match reads authorize the parent separately, and scans write matches by search ID after provider I/O. In a simulated transfer during that I/O, the old-scope scan returned 404 but persisted a match under the new scope. Join match reads to the scoped parent and recheck ownership in the same write transaction as match persistence. [Match reads](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/routes/product.py:261) · [Scan writes](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/routes/product.py:337)
