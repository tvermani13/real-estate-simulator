# Consultant response: Hearthline H1b platform principal

Date: 2026-11-22. Reviewer: the independent consultant, read-only access to this repository and the platform repository. Verbatim final review below, then what was applied.

### 1. Principal and middleware — Correct credential precedence, changes required before enablement

A present `X-Platform-Context`, including an empty value, selects platform authentication on protected routes. A refusal never falls back to the legacy session, and a valid context supplies both workspace and subject. Keep that behavior and the refusal on legacy register, login, and logout. This matches K1’s credential decision. [Hearthline principal](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/auth.py:182) · [K1 review](/Users/tejasvermani/Developer/platform-3a-adr/docs/decisions/consultant-reviews/2026-11-22-3a-k1-native-first.response.md:11)

- **Read legacy credentials only in the legacy branch.** FastAPI resolves the declared `Header` and `Cookie` parameters before calling `current_principal`. The platform branch skips the legacy session lookup, but the framework still extracts both credentials. Make the dependency take `Request` and defer extraction until after the platform branch. Reject multiple context header fields before selecting a value. On the platform route, have the edge strip client-supplied platform headers and legacy credentials, then inject exactly one context. [Principal dependency](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/auth.py:182) · [Edge header forwarding](/Users/tejasvermani/Developer/platform-3a-adr/edge/src/modules.ts:45)
- **Require an exact origin and cover error responses.** The edge checks a supplied `Origin` against the module origin, while FastAPI only checks for a nonempty value. Make the edge require exactly one matching origin before minting for Hearthline writes, and enforce the same configured origin in FastAPI. Wrap the full FastAPI ASGI app so uncaught `500` responses also receive `private, no-store`. Apply that policy at ingress to private responses generated there as well. [Edge origin check](/Users/tejasvermani/Developer/platform-3a-adr/edge/src/modules.ts:118) · [FastAPI middleware setup](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/main.py:31) · [Starlette middleware ordering](https://starlette.dev/middleware/#using-middleware)
- **Fix the verifier upstream and re-vendor it.** The loopback check validates the configured URL, but the fetch uses an opener that follows redirects and honors proxy settings. Pin a literal loopback endpoint, disable redirects and proxy discovery, and return controlled denials for malformed contexts or unusable key sets. Pass `contract_version="1"` explicitly. Initialize one verifier before serving traffic, or synchronize its creation. Its replay cache currently evicts live entries when full. Require atomic reservation through the last instant the verifier can accept the token, and refuse writes at capacity. One process and one in-memory cache are sufficient for this pilot. [Hearthline verifier setup](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/app/core/platform.py:59) · [Vendored verifier source](/Users/tejasvermani/Developer/platform-3a-adr/adapters/python/platform_context/verifier.py:53) · [Python URL handling](https://docs.python.org/3.11/library/urllib.request.html)

### 2. Staging network — Use host networking with explicit loopback binds

For the documented Linux DGX layout, put the staging backend on the host network and bind Uvicorn explicitly to `127.0.0.1` with one worker. Override the image’s `0.0.0.0` command as part of the same change. Keep JWKS on the host edge’s loopback listener. Give the edge a loopback gateway upstream that routes `/api` to the loopback backend and the UI to the frontend. The current bridge gateway’s `backend:8000` target needs to change in that topology. Check actual listeners and Tailscale Serve mappings, preserve a separate authorized legacy ingress during the pilot, and replace wildcard forwarded-header trust with trust in the actual proxy hops. The rate limiter should use an address established by that chain. [Backend image](/Users/tejasvermani/Developer/hearthline-3a-scope/backend/Dockerfile:25) · [Caddy routing](/Users/tejasvermani/Developer/hearthline-3a-scope/infra/Caddyfile:13) · [DGX runbook](/Users/tejasvermani/Developer/hearthline-3a-scope/docs/RUNBOOK.md:27) · [Docker host networking](https://docs.docker.com/engine/network/drivers/host/)

A sidecar is viable if it shares the backend’s network namespace and reaches the authoritative edge key set over an authenticated local channel, such as a permissioned Unix socket. A separate bridge container still has its own loopback. A non-loopback endpoint would require a reviewed ADR change for a specific authenticated endpoint, with restrictive network policy and an explicit identity check such as mTLS. A private IP allowlist alone is insufficient. [Platform transport contract](/Users/tejasvermani/Developer/platform-3a-adr/contracts/request-context/v1/README.md:19)

### 3. Vendoring — Keep the relative path and verify before install

The provenance is adequate. I verified the wheel SHA-256 and matched all five packaged Python files byte-for-byte to the recorded platform commit. The four vendoring tests passed. The gap is timing. ADR 0012 requires verification **before install**, and today the tests run afterward. Use a standard-library SHA-256 check that fails the Docker build, CI, and bootstrap before pip installs the wheel. Keep the installed-copy test and the pinned transitive dependencies. That satisfies this gate without requiring pip hash mode for the entire lock, which would require hashes for every dependency.
